## 1. Why Local State Falls Apart

By default, Terraform keeps its state in a single file, `terraform.tfstate`, on disk in the same directory as your code. This works fine for a solo experiment, but breaks down quickly in any real team setting:

| Problem | Why it matters |
|---|---|
| **Single point of failure** | If your laptop dies or the file is deleted, Terraform loses track of every resource it manages — it can no longer map your code to real infrastructure. |
| **No collaboration** | Two people can't safely run `terraform apply` from their own local copies — state changes made by one person are invisible to the other. |
| **No versioning** | You can't see who changed what, or roll back to a previous known-good state. |
| **No locking** | Nothing stops two applies from running at once and corrupting the file. |

The natural first instinct is "put it in Git alongside the code" — see why that's a bad idea below.

---

## 2. Using Git for Terraform Code

Git is still the right home for your **Terraform code** (`.tf` files) — just not for the **state file**. Benefits of Git for the code itself:

1. **Central source of truth** — everyone works from the same repo.
2. **Version history** — every change is tracked and revertible.
3. **Code review** — changes go through Pull Requests before merging.
4. **CI/CD integration** — `plan`/`apply` can be automated on merge.

> **Practice:** always push code changes as a Pull Request and get a peer review before merging — never push straight to the main branch.

## 3. Security Risks of Storing State in Git

The state file is a **plain-text JSON snapshot** of every resource attribute Terraform knows about — including sensitive values like database passwords. Committing it to Git means:

- Secrets sit in plain text inside your repo history (removing the file later doesn't remove it from history).
- If the repo is public — or later becomes public, or a laptop with repo access is compromised — those secrets are exposed.

### Demonstration: password leaking into state

```hcl
resource "aws_db_instance" "default" {
  allocated_storage    = 10
  db_name              = "mydb"
  engine               = "mysql"
  engine_version       = "8.0"
  instance_class       = "db.t3.micro"
  username             = "foo"
  password             = "foobarbaz#321"
  parameter_group_name = "default.mysql8.0"
  skip_final_snapshot  = true
}
```

```bash
terraform apply -auto-approve
# Inspect terraform.tfstate — the password is stored in plain text
terraform destroy -auto-approve
```

### A common (but incomplete) mitigation: `file()` function

Reading the password from an external file keeps it out of your `.tf` source code:

```hcl
resource "aws_db_instance" "default" {
  allocated_storage    = 10
  db_name              = "mydb"
  engine               = "mysql"
  engine_version       = "8.0"
  instance_class       = "db.t3.micro"
  username             = "foo"
  password             = file("outside-folder/pass.txt")
  parameter_group_name = "default.mysql8.0"
  skip_final_snapshot  = true
}
```

```bash
terraform apply -auto-approve
# Inspect terraform.tfstate again — the password is STILL there in plain text
terraform destroy -auto-approve
```

> **Key takeaway:** `file()` only hides the secret from your *source code* — it does nothing to protect the *state file*, because Terraform records the resolved attribute value in state regardless of where the value came from. The real fix is to never let the state file itself land anywhere insecure (see [Terraform Backends](#5-terraform-backends)), and to use a secrets manager (e.g. AWS Secrets Manager, Vault) rather than a plain file for genuinely sensitive values.

## 4. Terraform & .gitignore

### Files to keep OUT of Git

| File / pattern | Reason |
|---|---|
| `.terraform/` | Local cache of provider plugins and modules — large, and machine-specific. |
| `terraform.tfstate` / `terraform.tfstate.backup` | Contains resource attributes, which can include sensitive data. |
| `*.tfvars` (when they contain secrets) | Input variable files often carry credentials or environment-specific secrets. |
| `crash.log` | Debug dump written automatically if Terraform crashes — may contain sensitive data from state/plan. |
| `.terraform.tfstate.lock.info` | Transient lock metadata, created/deleted automatically during operations. |
| Saved plan files (from `terraform plan -out=<file>`) | A plan file can contain sensitive values resolved at plan time. |

### Suggested `.gitignore`

```gitignore
# Local .terraform directories
**/.terraform/*

# .tfstate files
*.tfstate
*.tfstate.*

# Crash log files
crash.log
crash.*.log

# Exclude sensitive variable files
*.tfvars
*.tfvars.json

# Ignore override files
override.tf
override.tf.json
*_override.tf
*_override.tf.json

# Include tfplan files if you'd like to keep versions of it
*tfplan*
```

### What you SHOULD commit

- All Terraform code (`.tf` files)
- The `.terraform.lock.hcl` dependency lock file (pins provider versions for reproducibility)
- A `.gitignore` that excludes the files above
- A `README.md` describing the module's purpose, input variables, and outputs

## 5. Terraform Backends

A **backend** determines *where* Terraform stores its state file and how operations (plan/apply) read and write to it.

- If no backend is configured, Terraform uses the **default `local` backend** — state lives as `terraform.tfstate` in the working directory.
- **Recommended pattern:**
  - Terraform **code** → Git
  - Terraform **state** → a central remote backend

### Commonly supported backends

| Backend | Notes |
|---|---|
| `local` | Default; state stored on disk. Not suitable for teams. |
| `s3` | AWS-native; supports state locking. Most widely used for AWS workloads. |
| `azurerm` | Azure-native equivalent of S3 backend. |
| `gcs` | Google Cloud Storage — GCP-native equivalent. |
| `consul` | HashiCorp Consul KV store. |

📖 Reference: [Terraform Backend docs](https://developer.hashicorp.com/terraform/language/backend) · [Local backend](https://developer.hashicorp.com/terraform/language/backend/local)

### Explicit local backend example

```hcl
resource "aws_security_group" "prod" {
  name = "production-sg"
}

terraform {
  backend "local" {
    path = "prod.tfstate"
  }
}
```

```hcl
resource "local_file" "example" {
  filename = "hello.txt"
  content  = "Hello Terraform!"
}
```

> Running `terraform apply` with the above config creates a `prod.tfstate` file at the specified path instead of the default `terraform.tfstate`.

### Remote backends — key characteristics

- Backends like S3 typically require **authentication** to the target cloud provider before Terraform can read/write state.
- Some backends act as simple "remote disks" (just store the file remotely); others additionally support **state locking** (see next section) — S3 supports both.

## 6. State Locking

### The problem

If two team members run `terraform apply` **at the same time** against the same state, Terraform can make concurrent, conflicting writes — corrupting the state file or leaving it inconsistent with real infrastructure.

### The solution: locking

State locking prevents concurrent operations from modifying the state simultaneously:

1. Terraform attempts to **acquire a lock** on the state before an operation.
2. If the lock succeeds, the operation (plan/apply) proceeds.
3. Once the operation finishes, Terraform **releases the lock**.
4. If a second operation tries to run while the lock is held, Terraform errors out, reporting the state is locked.

- **Local backend:** lock is represented by a `.terraform.tfstate.lock.info` file alongside the state.
- **S3 backend:** locking is handled either via native S3 conditional writes (`use_lockfile`, newer Terraform versions) or historically via a **DynamoDB table** (`dynamodb_table` argument, older/common pattern).

### Demonstrating a lock

```hcl
resource "time_sleep" "wait_100_seconds" {
  create_duration = "100s"
}
```

```bash
terraform init
terraform apply -auto-approve
# While that apply is running (sleeping), open a second terminal:
terraform plan
# -> Error: state is locked
```

📖 Reference: [`time_sleep` resource](https://registry.terraform.io/providers/hashicorp/time/latest/docs/resources/sleep.html)

## 7. S3 Backend

Stores the state file in an S3 bucket, giving you a central, durable, versionable location for state — and, with locking enabled, safe concurrent access.

📖 Reference: [S3 backend docs](https://developer.hashicorp.com/terraform/language/backend/s3)

### Example configuration

`sg.tf`:
```hcl
resource "aws_security_group" "prod" {
  name = "production-sg"
}
```

`backend.tf`:
```hcl
terraform {
  backend "s3" {
    bucket       = "labs-demo-bucket-001"   # must be a bucket you own — change before use
    key          = "production.tfstate"
    region       = "us-east-1"
    use_lockfile = true
  }
}
```

> **Note:** `use_lockfile` is a boolean, so it should be `true`/`false` without quotes (`"true"` as a string can cause unexpected behavior in HCL). This enables S3's native locking mechanism (via conditional writes), which is the modern replacement for the older DynamoDB-table-based locking pattern.

```bash
terraform init
terraform apply -auto-approve
```

## 8. State Management Commands

> ⚠️ **Never manually edit `terraform.tfstate` by hand.** Use the `terraform state` subcommands — they exist specifically for safe, controlled state manipulation.

| Command | Purpose |
|---|---|
| `terraform state list` | List all resources currently tracked in state. |
| `terraform state show <address>` | Show all attributes of a single tracked resource. |
| `terraform state mv <src> <dst>` | Move/rename an item within state (e.g. after renaming a resource in code). |
| `terraform state rm <address>` | Remove an item from state **without destroying the real infrastructure** — Terraform simply "forgets" it. |
| `terraform state pull` | Manually download and print the current remote state. |
| `terraform state push` | Manually upload a local state file to the remote backend (rarely needed; risky). |
| `terraform state replace-provider <from> <to>` | Update the provider source associated with resources in state (e.g. after a provider fork/rename). |

### Worked example

```hcl
terraform {
  backend "s3" {
    bucket = "kplabs-terraform-backends"
    key    = "demo.tfstate"
    region = "us-east-1"
  }
}

resource "aws_iam_user" "dev" {
  name = "kplabs-user-01"
}

resource "aws_security_group" "prod" {
  name = "terraform-firewalls"
}
```

**1. List resources managed by Terraform:**
```bash
terraform state list
```

**2. Show attributes of a resource:**
```bash
terraform state show aws_security_group.prod
```

**3. Pull the state file from the remote backend:**
```bash
terraform state pull
```

**4. Remove resources from state** (e.g. before decommissioning management of them):

```hcl
resource "aws_vpc_security_group_ingress_rule" "example" {
  security_group_id = aws_security_group.prod.id
  cidr_ipv4          = "10.0.0.0/8"
  from_port          = 80
  ip_protocol        = "tcp"
  to_port            = 80
}

resource "aws_vpc_security_group_ingress_rule" "example2" {
  security_group_id = aws_security_group.prod.id
  cidr_ipv4          = "10.0.0.0/8"
  from_port          = 80
  ip_protocol        = "tcp"
  to_port            = 80
}
```

```bash
terraform state rm aws_security_group.prod
terraform state rm aws_vpc_security_group_ingress_rule.example
terraform state rm aws_vpc_security_group_ingress_rule.example2
```

**5. Move/rename a resource address** (e.g. `dev` user is now `prod`):
```bash
terraform state mv aws_iam_user.dev aws_iam_user.prod
```

**6. Replace a resource's provider** (e.g. migrating to an internal provider fork):
```bash
terraform state replace-provider hashicorp/aws kplabs.in/internal/aws
```

📖 Reference: [`aws_vpc_security_group_ingress_rule`](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/vpc_security_group_ingress_rule)

## 9. Cross-Project Collaboration via Remote State Data Source

**Scenario:** different teams manage different slices of infrastructure, but sometimes need each other's outputs.

- **Networking team** provisions an Elastic IP and needs to publish its address.
- **Security team** needs that IP to whitelist it in a security group — without owning or duplicating the networking team's code.

The `terraform_remote_state` data source lets one project read another project's **state outputs** (read-only) without merging codebases.

📖 References: [Remote State Data Source](https://developer.hashicorp.com/terraform/language/state/remote-state-data) · [S3 Backend settings](https://developer.hashicorp.com/terraform/language/settings/backends/s3)

### Step 1 — Set up two project folders

```bash
mkdir networking-team security-team
cd networking-team
```

### Step 2 — Networking team: create the EIP and expose an output

`eip.tf`:
```hcl
resource "aws_eip" "lb" {
  domain = "vpc"
}

output "eip_addr" {
  value = aws_eip.lb.public_ip
}
```

`backend.tf`:
```hcl
terraform {
  backend "s3" {
    bucket = "kplabs-networking-bucket-demo"
    key    = "eip.tfstate"
    region = "us-east-1"
  }
}
```

```bash
terraform init
terraform plan
terraform apply -auto-approve
```

### Step 3 — Security team: read the networking team's state

```bash
cd ../security-team
```

`data.tf`:
```hcl
data "terraform_remote_state" "vpc" {
  backend = "s3"

  config = {
    bucket = "kplabs-networking-bucket-demo"
    key    = "eip.tfstate"
    region = "us-east-1"
  }
}
```

### Step 4 — Security team: consume the output in a security group rule

`sg.tf`:
```hcl
resource "aws_security_group" "allow_tls" {
  name = "allow_tls"
}

resource "aws_vpc_security_group_ingress_rule" "allow_tls_ipv4" {
  security_group_id = aws_security_group.allow_tls.id
  cidr_ipv4          = "${data.terraform_remote_state.vpc.outputs.eip_addr}/32"
  from_port          = 443
  ip_protocol        = "tcp"
  to_port            = 443
}
```

> The security team never touches the networking team's `.tf` files or state directly — they only read a declared **output**, which keeps ownership boundaries clean and avoids tight coupling between teams.

## 10. Terraform Import

**Scenario:** infrastructure was created manually (console/CLI) before your org adopted Terraform. You now want Terraform to manage it going forward, without recreating it.

### Legacy workflow (pre-1.5)

```
manually created resource → terraform import <address> <id> → terraform.tfstate
```

This updated state to track the resource, but you still had to hand-write the matching `.tf` configuration yourself — error-prone and slow.

### Modern workflow (Terraform 1.5+): `import` blocks

Terraform can now **generate the matching configuration automatically**, saving significant time and reducing drift between real infra and written code.

`import.tf`:
```hcl
provider "aws" {
  region = "us-east-1"
}

import {
  to = aws_security_group.mysg
  id = "sg-07f13feb262ba8b6f"
}
```

**Step 1 — Auto-generate the `.tf` configuration for the imported resource:**
```bash
terraform plan -generate-config-out=mysg.tf
```

**Step 2 — Apply to finalize the import into state:**
```bash
terraform apply -auto-approve
```

> After this, review the generated `mysg.tf` carefully — auto-generated config is a strong starting point but should be checked against your module's conventions before being treated as final.

## 11. Removed Blocks

**Scenario:** a resource should no longer be managed by Terraform, but you do **not** want it destroyed — you just want Terraform to "let go" of it.

### Old approaches

- Run `terraform state rm <address>` manually, **or**
- Delete/comment out the resource block in code (risky — if done without `state rm` first, the next `apply` will try to *destroy* the real resource).

### Modern approach: `removed` block (Terraform 1.7+)

A `removed` block declares, in code, that a resource should be removed from state **without destroying the underlying infrastructure** — and it's reviewable via a normal plan/PR just like any other config change.

```hcl
removed {
  from = aws_instance.myec2

  lifecycle {
    destroy = false
  }
}
```

- `from` — the resource address to stop managing.
- `lifecycle { destroy = false }` — tells Terraform to drop the resource from state **without** destroying the real infrastructure. (Setting `destroy = true` would instead have Terraform destroy the resource as part of removing it from state — useful for a controlled decommission.)

> **Corrections applied to source notes:** the block keyword is `removed` (not `removoved`), the lifecycle argument is `destroy` (not `desstroy`), and the resource address syntax is `aws_instance.myec2` (underscore, not a dot after `aws`) — `aws.instance.myec2` is not valid Terraform resource address syntax.

## Quick Reference Summary

| Topic | Key Command / Concept |
|---|---|
| Keep state out of Git | `.gitignore`: `*.tfstate`, `.terraform/`, `*.tfvars` |
| Central state storage | `backend "s3" { ... }` |
| Prevent concurrent writes | State locking (`use_lockfile` / DynamoDB) |
| Inspect/modify state safely | `terraform state list / show / mv / rm / pull / push / replace-provider` |
| Share outputs across teams | `data "terraform_remote_state"` |

| Stop managing a resource (keep it alive) | `removed` block with `destroy = false` |
