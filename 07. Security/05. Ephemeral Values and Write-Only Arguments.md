# Terraform – Ephemeral Values and Write-Only Arguments

**Date:** 27 August 2026

## 1. What Problem Are We Solving?

When working with sensitive values such as:

* Database passwords
* API keys
* Tokens
* AWS credentials
* Secrets Manager values

we do not want those values unnecessarily persisted in Terraform state.

A traditional Terraform approach can result in a generated password being stored in state.

Terraform provides newer features to address this:

> **Ephemeral values** and **write-only arguments**.

---

# 2. Traditional Approach

The traditional configuration uses `random_password`:

```hcl
resource "random_password" "db_password" {
  length           = 16
  override_special = "!#$%&*()-_=+[]{}<>:?"
}

resource "aws_db_instance" "default" {
  allocated_storage = 10
  db_name           = "mydb"
  engine            = "mysql"
  engine_version    = "8.0"
  instance_class    = "db.t3.micro"
  username          = "foo"

  password = random_password.db_password.result

  skip_final_snapshot = true
}

output "db_password" {
  value     = random_password.db_password.result
  sensitive = true
}
```

The password is marked:

```hcl
sensitive = true
```

but this only prevents the value from being displayed normally.

### Important

**Sensitive does NOT mean ephemeral.**

A sensitive value can still be stored in Terraform state.

---

# 3. Traditional Flow

```text
random_password
      |
      | password
      ↓
aws_db_instance
      |
      ↓
Terraform State
```

Even though the output is marked sensitive:

```hcl
sensitive = true
```

the password can still be persisted in state.

---

# 4. Ephemeral Values

An **ephemeral value** is a value that exists only temporarily during Terraform operations and is not persisted in Terraform state.

Example:

```hcl
ephemeral "random_password" "db_password" {
  length           = 16
  override_special = "!#$%&*()-_=+[]{}<>:?"
}
```

The key difference is:

```hcl
ephemeral
```

instead of:

```hcl
resource
```

The generated password is available when Terraform needs it, but Terraform does not persist the ephemeral result in state.

---

# 5. Write-Only Arguments

A **write-only argument** allows Terraform to send a sensitive value to a resource without reading that value back and storing it in Terraform state.

For example, AWS RDS supports:

```hcl
password_wo
```

instead of:

```hcl
password
```

The `_wo` means:

> **Write Only**

Example:

```hcl
resource "aws_db_instance" "default" {
  allocated_storage = 10
  db_name           = "mydb"
  engine            = "mysql"
  engine_version    = "8.0"
  instance_class    = "db.t3.micro"
  username          = "foo"

  password_wo         = ephemeral.random_password.db_password.result
  password_wo_version = 3

  skip_final_snapshot = true
}
```

---

# 6. Why Do We Need `password_wo_version`?

Write-only values cannot be read back by Terraform.

Therefore, Terraform needs another way to know when the password should be updated.

That is the purpose of:

```hcl
password_wo_version = 3
```

Think of it as a **change trigger**.

For example:

```text
password_wo_version = 1
        ↓
Password version 1

Change to:

password_wo_version = 2
        ↓
Terraform knows the password should be updated
```

The actual password does not need to be stored in state for Terraform to detect the version change.

---

# 7. AWS Secrets Manager

The password can also be written to AWS Secrets Manager.

First create the secret:

```hcl
resource "aws_secretsmanager_secret" "db_password" {
  name = "db_pass"
}
```

This creates the Secrets Manager secret container.

---

# 8. Store the Password in Secrets Manager

The secret value can then be written using:

```hcl
resource "aws_secretsmanager_secret_version" "db_password" {
  secret_id = aws_secretsmanager_secret.db_password.id

  secret_string_wo         = ephemeral.random_password.db_password.result
  secret_string_wo_version = 3
}
```

Notice the use of:

```hcl
secret_string_wo
```

This is another **write-only argument**.

The secret is written to AWS Secrets Manager but is not read back and persisted in Terraform state as the secret value.

---

# 9. Reading the Secret Ephemerally

The configuration can also use an ephemeral Secrets Manager data source:

```hcl
ephemeral "aws_secretsmanager_secret_version" "db_password" {
  secret_id = aws_secretsmanager_secret_version.db_password.secret_id
}
```

The important keyword is:

```hcl
ephemeral
```

This means the retrieved secret is intended to exist only temporarily during the Terraform operation.

---

# 10. Complete Example

```hcl
ephemeral "random_password" "db_password" {
  length           = 16
  override_special = "!#$%&*()-_=+[]{}<>:?"
}

resource "aws_db_instance" "default" {
  allocated_storage = 10
  db_name           = "mydb"
  engine            = "mysql"
  engine_version    = "8.0"
  instance_class    = "db.t3.micro"
  username          = "foo"

  password_wo         = ephemeral.random_password.db_password.result
  password_wo_version = 3

  skip_final_snapshot = true
}

resource "aws_secretsmanager_secret" "db_password" {
  name = "db_pass"
}

resource "aws_secretsmanager_secret_version" "db_password" {
  secret_id = aws_secretsmanager_secret.db_password.id

  secret_string_wo         = ephemeral.random_password.db_password.result
  secret_string_wo_version = 3
}

ephemeral "aws_secretsmanager_secret_version" "db_password" {
  secret_id = aws_secretsmanager_secret_version.db_password.secret_id
}
```

---

# 11. Overall Flow

```text
                Generate Password
                       |
                       ↓
          ephemeral.random_password
                       |
             +---------+---------+
             |                   |
             ↓                   ↓
       AWS RDS              AWS Secrets Manager
             |                   |
      password_wo          secret_string_wo
             |                   |
             ↓                   ↓
        Write Only           Write Only
```

The password is therefore passed to the required destinations without unnecessarily persisting the actual secret value in Terraform state.

---

# 12. Sensitive vs Ephemeral vs Write-Only

| Feature            | Purpose                                                       | Value stored in state? |
| ------------------ | ------------------------------------------------------------- | ---------------------- |
| `sensitive = true` | Hides value from normal CLI output                            | **Can be yes**         |
| `ephemeral`        | Prevents temporary values from being persisted                | **No**                 |
| `password_wo`      | Sends a value to a resource without reading it back           | **No secret value**    |
| `secret_string_wo` | Writes secret to Secrets Manager without persisting the value | **No secret value**    |
| `_wo_version`      | Tracks changes to a write-only value                          | Version is stored      |

---

# 13. `sensitive` vs `ephemeral`

This distinction is very important for interviews.

### Sensitive

```hcl
variable "password" {
  type      = string
  sensitive = true
}
```

Means:

> **Don't show this value in normal Terraform output.**

But the value may still exist in state.

### Ephemeral

```hcl
ephemeral "random_password" "db_password" {
  ...
}
```

Means:

> **This value is temporary and should not be persisted in Terraform state.**

---

# 14. Why Write-Only Arguments Are Useful

Consider an RDS password.

Traditional:

```hcl
password = var.password
```

Terraform may need to keep the password in state.

With a write-only argument:

```hcl
password_wo = var.password
```

Terraform sends the password to AWS but does not need to store the actual password value in state.

# 16. Interview Questions

### Q1. What is an ephemeral value?

**Answer:**

An ephemeral value is a temporary value that Terraform can use during an operation without persisting the value in Terraform state.

---

### Q2. What is a write-only argument?

**Answer:**

A write-only argument allows Terraform to send a value to a resource without reading the value back or storing the actual value in Terraform state.

Examples include:

```hcl
password_wo
secret_string_wo
```

---

### Q3. What is the difference between `sensitive` and `ephemeral`?

**Answer:**

`sensitive = true` hides a value from normal Terraform output, but the value may still be stored in state.

An ephemeral value is designed not to be persisted in Terraform state.

---

### Q4. Why is `password_wo_version` required?

**Answer:**

Because Terraform cannot read the write-only password back. The version number provides a mechanism for Terraform to detect that the write-only value needs to be updated.

Example:

```hcl
password_wo_version = 3
```

Changing the version can trigger an update.

---

### Q5. What does `_wo` mean?

**Answer:**

`_wo` means **write-only**.

Examples:

```text
password_wo
secret_string_wo
```

The value can be written to the target system but is not read back into Terraform state.

---

### Q6. Why use Vault or AWS Secrets Manager with ephemeral values?

**Answer:**

They provide dedicated secret-management capabilities. Terraform can retrieve or generate a secret temporarily and pass it to the required resource without unnecessarily persisting the secret value in Terraform state.

---

# Key Takeaway

> **`sensitive` hides a value from Terraform output, while `ephemeral` prevents temporary values from being persisted in state. Write-only arguments such as `password_wo` and `secret_string_wo` allow Terraform to send secrets to resources without reading the secret value back. Version arguments such as `password_wo_version` allow Terraform to detect changes to write-only values.**
