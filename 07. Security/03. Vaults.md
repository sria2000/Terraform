# Terraform – Multiple Provider Configurations & Vault

**Date:** 27 August 2026
**Topic:** Multiple Provider Configurations / HashiCorp Vault

---

## 1. What is HashiCorp Vault?

**HashiCorp Vault** is a secrets-management tool used to securely store and access sensitive information.

Examples of secrets include:

* Database passwords
* API keys
* AWS credentials
* Certificates
* Tokens
* Encryption keys
* Application secrets

Instead of hardcoding passwords in Terraform code:

```hcl
password = "supersecretpassw0rd"
```

we can store the secret in Vault and retrieve it when required.

---

# 2. Why Use Vault with Terraform?

A typical environment may look like:

```text
              HashiCorp Vault
                     |
        +------------+------------+
        |            |            |
   DB Password    AWS Keys    Certificates
        |
        ↓
     Terraform
        |
        ↓
   AWS Resources
```

The main benefit is that sensitive information does not need to be hardcoded directly into Terraform configuration.

---

# 3. Vault Provider

Terraform communicates with Vault using the **Vault provider**.

Basic provider configuration:

```hcl
provider "vault" {
  address = "http://127.0.0.1:8200"
}
```

### Explanation

| Argument           | Meaning                                   |
| ------------------ | ----------------------------------------- |
| `provider "vault"` | Configures the HashiCorp Vault provider   |
| `address`          | URL/address of the Vault server           |
| `127.0.0.1:8200`   | Local Vault server listening on port 8200 |

> **Production:** Vault should normally be accessed over HTTPS and authenticated using an appropriate Vault authentication method rather than relying on a locally configured development setup.

---

# 4. Reading a Secret from Vault

Terraform can read an existing secret using a Vault data source:

```hcl
data "vault_generic_secret" "demo" {
  path = "secret/db_creds"
}
```

Here:

```text
secret/db_creds
```

is the path where the secret is stored in Vault.

Terraform does not create this secret. It **reads an existing secret** from Vault.

---

# 5. Outputting the Vault Secret

The secret can be accessed using:

```hcl
data.vault_generic_secret.demo.data_json
```

For example:

```hcl
output "vault_secrets" {
  value     = data.vault_generic_secret.demo.data_json
  sensitive = true
}
```

The important part is:

```hcl
sensitive = true
```

This prevents Terraform from displaying the secret normally in CLI output.

---

# 6. Complete Example

```hcl
provider "vault" {
  address = "http://127.0.0.1:8200"
}

data "vault_generic_secret" "demo" {
  path = "secret/db_creds"
}

output "vault_secrets" {
  value     = data.vault_generic_secret.demo.data_json
  sensitive = true
}
```

### Flow

```text
Vault
  |
  | secret/db_creds
  ↓
vault_generic_secret
  |
  ↓
data.vault_generic_secret.demo.data_json
  |
  ↓
Terraform
  |
  ↓
Sensitive output
```

# 7. Example Secret

Suppose Vault contains:

```text
Path:
secret/db_creds
```

with values such as:

```text
username = admin
password = MySecretPassword
```

Terraform reads the secret using:

```hcl
data "vault_generic_secret" "demo" {
  path = "secret/db_creds"
}
```

The secret can then be consumed by another Terraform resource.

For example:

```hcl
resource "some_database" "db" {
  username = data.vault_generic_secret.demo.data["username"]
  password = data.vault_generic_secret.demo.data["password"]
}
```

The exact resource syntax depends on the provider/resource being used.

# 8. Multiple Provider Configurations

Terraform can have multiple configurations of the **same provider**.

For example, with AWS:

```hcl
provider "aws" {
  region = "ap-southeast-1"
}

provider "aws" {
  alias  = "mumbai"
  region = "ap-south-1"
}
```

The first is the default AWS provider.

The second uses the alias:

```text
aws.mumbai
```

A resource can explicitly select the provider:

```hcl
provider = aws.mumbai
```

---

# 9. Multiple Vault Provider Configurations

The same alias concept can be used when multiple Vault provider configurations are required.

Example:

```hcl
provider "vault" {
  address = "https://vault-prod.example.com"
}

provider "vault" {
  alias   = "dev"
  address = "https://vault-dev.example.com"
}
```

The default provider is:

```text
vault
```

The additional provider is:

```text
vault.dev
```

A data source can then select the required Vault instance:

```hcl
data "vault_generic_secret" "dev_secret" {
  provider = vault.dev
  path     = "secret/db_creds"
}
```

---

# 10. Important Concepts

| Concept                | Meaning                                                    |
| ---------------------- | ---------------------------------------------------------- |
| Provider               | Allows Terraform to communicate with an external platform  |
| Vault provider         | Allows Terraform to communicate with HashiCorp Vault       |
| Data source            | Reads existing information                                 |
| `vault_generic_secret` | Reads a secret from Vault                                  |
| `alias`                | Distinguishes multiple configurations of the same provider |
| `sensitive = true`     | Prevents sensitive values from being displayed normally    |
| Vault                  | Centralised secrets-management system                      |

---

# 11. Why Vault Instead of Hardcoding Passwords?

### Bad practice

```hcl
resource "aws_db_instance" "database" {
  password = "MyPassword123"
}
```

The password is directly visible in the Terraform configuration.

### Better approach

```text
             Vault
               |
          DB Password
               |
               ↓
           Terraform
               |
               ↓
          AWS Database
```

Terraform retrieves the password from Vault rather than putting the password directly into the configuration.

# 12. Interview Questions

### Q1. What is HashiCorp Vault?

**Answer:**

HashiCorp Vault is a secrets-management system used to securely store and access sensitive information such as passwords, API keys, certificates, tokens and credentials.

---

### Q2. Why would you use Vault with Terraform?

**Answer:**

To avoid hardcoding sensitive credentials in Terraform configuration and to centralise secret management.

---

### Q3. What is a Terraform data source?

**Answer:**

A data source allows Terraform to retrieve existing information from an external system or provider without creating that resource.

Example:

```hcl
data "vault_generic_secret" "demo" {
  path = "secret/db_creds"
}
```

---

### Q4. What does `sensitive = true` do?

**Answer:**

It tells Terraform to treat the value as sensitive and prevents it from being displayed normally in Terraform CLI output.

---

### Q5. Does `sensitive = true` completely secure the secret?

**Answer:**

**No.**

It hides the value from normal Terraform output, but sensitive values can still be present in Terraform state. The state file must therefore be properly secured.

---

### Q6. Can Terraform have multiple configurations of the same provider?

**Answer:**

**Yes.**

Additional configurations are normally given an alias.

Example:

```hcl
provider "aws" {
  region = "ap-southeast-1"
}

provider "aws" {
  alias  = "mumbai"
  region = "ap-south-1"
}
```

---

# Key Takeaway

> **Vault is used to centrally store and manage secrets, while Terraform's Vault provider allows Terraform to retrieve those secrets. Data sources read existing Vault secrets, and `sensitive = true` prevents sensitive values from being displayed normally. Multiple configurations of the same Terraform provider can be created using aliases.**
